## สรุปผลตรวจของ code review รอบสุดท้าย

review ไล่ทั้ง 16 ข้อแล้วเห็นด้วย 15 ข้อ และ **ค้าน 1 ข้อคือ R-10 (พอร์ต)**
โดยให้เหตุผลว่าไม่ใช่เพราะเลือกผิด แต่เพราะ**ขอบเขตผิด** — ปัญหาพอร์ตชนบนเครื่อง
พัฒนาเครื่องเดียวถูกฝังลง `app/vite.config.js` ที่ผู้ร่วมพัฒนาข้างนอกต้องรับไปด้วย
ทั้งที่เหตุไม่เคยใช้กับเขา และชี้ว่า **R-12 เป็นรูปแบบที่ถูก** คือตัดสินใจเหมือนกัน
แต่ไม่ฝังลงโค้ด เหลือทางสลับหนึ่งบรรทัดพร้อมตัวเลขวัดไว้ให้เจ้าของงานเลือก

นอกจากนี้ review พบว่า **เหตุผลที่อ้างใน R-11 ผิด** — `playwright-core` ตั้งใจไม่พา
เบราว์เซอร์มาเลย ทางถอยที่เขียนไว้จึงไม่มีอยู่จริง แก้ทั้งโค้ดและคำอธิบายแล้ว
(ตัวการตัดสินใจยังใช้ได้ คือใช้ Chrome ในเครื่อง แต่ต้องบอกให้ชัดว่าต้องมี Chrome)

## รายการทั้ง 16 ข้อ

### R-1 รูปแบบ import worker — ใช้ `mokhwan-engine/worker?worker` ก่อนตามแผน ถ้า Vite resolve ไม่ได้ให้เปลี่ยนเป็น relative path ไปที่ซอร์สแล้วไปต่อ พร้อมบันทึกใน BACKLOG — เพราะสเปก §8 เตือนไว้เองว่ายังไม่ยืนยัน และการหยุดถามเรื่องนี้ไม่คุ้ม — ถ้าผิด: Task 4 เสีย fix round เดียว และคนที่ npm i ไปใช้จะต้องตั้ง worker เอง (บันทึกไว้แล้ว)

### R-2 เลขบรรทัด 1546 ผิด (หลุดมาจาก smoke-plume-studio-3.html) — แก้เป็น 1827 ในแผน และเพิ่มกฎว่าทุก anchor ต้องหาด้วย grep เนื้อหา ไม่ใช่เลขบรรทัด grep ไม่เจอให้หยุดรายงาน — เพราะ app.js เลื่อนไป 865 บรรทัดจากไฟล์ตั้งต้น เลขจึงเชื่อไม่ได้ทั้งชุด — ถ้าผิด: implementer แก้ผิดตำแหน่งแล้วแอปพัง ซึ่ง Step 12 จับได้

### R-3 smoke test มีบรรทัดตาย (`runSim === undefined`) และเช็ค "ไม่คำนวณใหม่" ด้วยการเซ็ต `S.view` ตรงๆ ซึ่งไม่ทริกอะไร ผ่านฟรี — แก้ให้กดผ่าน DOM จริงโดย implementer หา selector จาก index.html เอง หาไม่เจอให้รายงานแล้วข้าม — เพราะ assertion ที่ผ่านฟรีแย่กว่าไม่มี assertion — ถ้าผิด: เสียการคุ้มกันข้อนี้ไปหนึ่งข้อ ได้คืนในแผน B ตอนมี bus

### R-4 Vite ลงที่ root ไม่ใช่ `-w mokhwan-engine` — เพราะ Vitest 3 ที่ root ใช้ Vite อยู่แล้ว แยกลงจะได้สองเวอร์ชันในต้นไม้เดียว — ถ้าผิด: ไม่มีผลเชิงพฤติกรรม แค่ hoisting ต่างไป

### R-5 `packages/engine/package.json` อ้าง `./src/worker.ts` และ `./dist/*` ที่ยังไม่มีระหว่าง T2→T3 — ปล่อยไว้ ไม่แก้ — เพราะ `exports` ที่ชี้ไฟล์หายจะ error เฉพาะเมื่อมีคน import ด้วยชื่อแพ็กเกจ ซึ่งเกิดครั้งแรกที่ T4 ตอนนั้นไฟล์ครบแล้ว — ถ้าผิด: T3 พังทันทีและเห็นชัด

### R-6 ป้ายเลขบรรทัดในคอมเมนต์ fixtures กำกวม (บล็อกแอป vs ไฟล์ตั้งต้น) — แก้ให้ระบุทั้งสองระบบ — เพราะเป็นคอมเมนต์ที่จะอยู่ในโค้ดถาวรและทำให้คนอ่านทีหลังหลง — ถ้าผิด: แค่คอมเมนต์เพี้ยน ไม่กระทบพฤติกรรม

### R-7 `dist.test.ts` ต้อง build ก่อนถึงจะผ่าน `npm test` เปล่าๆ จะแดง — รับไว้ ไม่แก้ — เพราะ Step 7 ของ T3 build ก่อนเสมอ และการใส่ guard คือ YAGNI — ถ้าผิด: คนรัน `npm test` สดๆ เจอเทสต์แดงงงๆ จดไว้ใน BACKLOG ได้

### R-8 ที่นั่ง implementer ย้ายมาที่ controller — controller เขียนไฟล์เองทีละไฟล์ ส่วน task reviewer / final reviewer ยังใช้ subagent ตามเดิม — เพราะ CLAUDE.md อนุญาต subagent ทำงานอ่าน/ออดิตไว้ชัดเจน จึงได้กลไก review ของ skill มาครบโดยไม่ละเมิดกฎ และไม่ต้องรอ user แก้ CLAUDE.md ซึ่งกระทบทุกโปรเจกต์ — ถ้าผิด: context ของ controller โตกว่าที่ skill ออกแบบไว้ และ fix loop เสียประโยชน์ "resume implementer ที่ context ยังอยู่" ไปหนึ่งข้อ

### C1 เป็น finding ที่ขัดกับข้อความในแผนเอง (Task 2 Step 10 สั่งไม่ให้ครอบโหมด puff) — ตัดสินให้ finding ชนะ แผนผิด — เพราะแผนสับสนระหว่าง "ล็อกผลที่ถูก" กับ "จับความพลาดจากการย้าย" ซึ่งเป็นสองหน้าที่ต่างกัน และ runPuff+windField คือ 229 บรรทัดที่ใหญ่และเสี่ยงที่สุดที่ Task 2 ต้องย้าย — ถ้าผิด: fixtures บวมขึ้น 2 เคส เทสต์ช้าขึ้น ~100ms และก้าว 5 ต้องอัปเดตค่าอ้างอิงของสองเคสนี้โดยตั้งใจ

### ถอนข้อสังเกต "puffTerrain ได้ 5.303 ไม่ใช่ 0 อาการอาจไม่ใช่ศูนย์ทุกกรณี" — เป็นผลจากบั๊กพิกัดของ fixture เอง แก้แล้วได้ 0.139 (0.16% ของพื้นราบ) ซึ่งสอดคล้องกับ HANDOFF ไม่ได้ค้าน — แจ้งผู้ใช้แก้คำแล้วเพราะเทิร์นก่อนรายงานผิดไป — ถ้าผิด: ก้าว 5 ตั้งต้นจากสมมติฐานที่ผิด

### I1 residual doseGrid.truncated ยัง false ทุกเคส — รับไว้ ไม่จัดฉาก แก้แต่คำอธิบายให้ตรง — เพราะต้องให้ค่าเฉลี่ย 24 ชม. เกิน 37.5 ถึงขอบโดเมน 10 กม. ซึ่งไม่เกิดจากการเผาแปลงเดียว การจัดฉากคือปั้น fixture เพื่อปลุกตัวชี้วัด ไม่ใช่คุ้มกันโค้ด — ถ้าผิด: เสียการคุ้มกัน 1 ฟิลด์ที่ over/overMaxKm ครอบทับอยู่แล้ว

### R-9 แก้ Minor สองข้อทันทีโดยไม่เปิด fix round/re-review รอบใหม่ — เพราะแต่ละข้อเป็นบรรทัดเดียว และทั้งคู่เป็นอันตรายที่ commit ก่อนหน้าของ task นี้สร้างขึ้นเอง (ยามที่กลบช่องได้ + ยามที่ไม่มีใครรัน) การปล่อยไว้เพื่อรักษากระบวนการแย่กว่าการแก้ · กฎ "minor ไม่เข้า loop" คือเรื่องไม่เปลืองรอบ review ไม่ใช่ห้ามแก้ — ถ้าผิด: การแก้สองบรรทัดนี้ไม่ผ่าน review รอบเจาะจง แต่ final whole-branch review จะเห็น

### R-10 เปลี่ยนพอร์ต dev 5173→5180 และ preview 5181 ต่างจากที่แผนระบุ — เพราะเครื่องพัฒนามีโปรเจกต์ j123 จอง 5173 ถาวร (รันมา 23 วัน) Vite เลื่อนพอร์ตเองทุกครั้ง ครั้งแรกหลงไปเปิดแอปของโปรเจกต์อื่น — ถ้าผิด: Task 5 ต้องใช้ 5180 ไม่ใช่ 5173 (จดไว้แล้ว)

### R-1 ไม่ต้องใช้ทางถอย — mokhwan-engine/worker?worker resolve ข้ามแพ็กเกจได้จริงทั้ง dev และ build — พิสูจน์แล้วจาก resource ที่โหลด

### R-11 ใช้ Chrome ในเครื่องผ่าน channel:'chrome' แทนการ npx playwright install chromium ตามที่แผนระบุ — เพราะประหยัดการดาวน์โหลด ~150 MB และมี fallback ไป chromium ที่ Playwright จัดมาถ้าไม่มี — ถ้าผิด: เครื่อง CI ที่ไม่มี Chrome จะไปใช้ fallback ซึ่งต้อง install ก่อน
